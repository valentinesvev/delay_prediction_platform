# Исходные требования к обработчику входного потока

Реализация и её фактические ограничения: [ndtp_ingestion/README.md](../ndtp_ingestion/README.md). Этот документ — проект требований; не все его пункты являются реализованными гарантиями.

## Ответственность

Отдельный долгоживущий процесс принимает TCP-соединения от NDTP-эмулятора, выполняет handshake, декодирует телематические пакеты и нормализует точки. REST API эмулятора на порту 18080 только настраивает его отправку; получатель пакетов — наш TCP-обработчик. Форматы пакетов и поля уточнять по `data/dataset/docs/Emulator-and-Telematic-Packets-Specification.md` и реальным пакетам.

На входе проверять обязательные ID и время, корректность координат, допустимые скорость/диапазоны, типы, порядок и дубли пакетов. Некорректные пакеты не должны попадать в валидированную таблицу; отказ одного пакета не останавливает поток. `packet_id`, `unit_id`, `tr_id`, `event_time`, `receive_time` и признак валидности использовать для трассировки и дедупликации. Сопоставление `unit_id` с `tr_id` должно иметь явный источник и понятную реакцию на неизвестное устройство.

## Общая база и контракт ML

- `telemetry`: по крайней мере `tr_id`, `event_time`, `receive_time`, `location_valid`, `lon`, `lat`, `speed` с типами, пригодными для `ml.db.DBConfig`. Желательно хранить также идентификаторы пакета и устройства с уникальным ограничением для повторной доставки. Время — UTC. В журнале может быть больше полей исходного пакета.
- `schedule_plan`: `tt_action_item_id`, `tr_id`, `time_begin`, `manual_fill` и `geom` в формате `POINT (lon lat)` либо отдельные `lon`, `lat`. Загружать только план; `time_fact_begin` не передавать модели. План поддерживать для текущих рейсов, включая остановку через 10–15 минут от времени прогноза.
- `predictions` создаёт и дописывает `ml.worker` в этой же базе. Входной процесс в эту таблицу не пишет прогнозы.

Индексы для оконного чтения: `telemetry(event_time)`, `telemetry(tr_id,event_time)`, `schedule_plan(time_begin)`; для API: `predictions(tr_id,t_forecast,id)`. При работе нескольких процессов использовать транзакции: ML не должен видеть наполовину загруженный план или пакет.

## Время, очистка, контроль

Принимать запоздавшие точки с исходным `event_time` и фактическим `receive_time`; не подменять одно время другим. Определить допустимую задержку приёма и политику обработки слишком старых и будущих точек. Для `ML_TIME_MODE=wall` должны поступать свежие данные; исторический реплей использует `stream`. Не включать в признаки сведения, полученные позднее момента `T`.

Этот же процесс периодически удаляет устаревшие строки из `telemetry`, `schedule_plan` и `predictions` по **разным настраиваемым срокам**. Окно хранения телеметрии должно покрывать как минимум `ML_WINDOW_S` плюс запас на запаздывание; план — период использования маршрута; прогнозы — требуемую историю интерфейса. Для `predictions` очистка по `predicted_at`, для телеметрии — по согласованному правилу `event_time`/`receive_time`; не удалять план, ещё нужный текущему рейсу. Настройки и действия очистки логировать.

Метрики/логи: количество принятых, отброшенных и повторных пакетов, отставание по времени, последняя запись по ТС, длительность записи и очистки, ошибки БД и реконнекты. Нагрузочные и интеграционные проверки: дубли, запоздавшие и повреждённые пакеты, недоступная БД, рестарт процесса, план без ТС, одновременная запись и чтение, отсутствие свежей телеметрии. Для отдельного исторического режима остаётся `ml.csv_to_db`.
