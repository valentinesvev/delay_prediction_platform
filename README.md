# Delay Prediction Platform

## Работа с репозиторием

> **Важно:** если вы загружаете новую библиотеку, добавьте её в `requirements.txt` и закоммитьте это изменение. 

#### 1. Клонируйте репозиторий

```bash
git clone https://github.com/valentinesvev/delay_prediction_platform.git
cd delay_prediction_platform
```

#### 2. Создайте свою ветку

Обновите `main` и создайте от неё ветку командой `git switch -c`:

```bash
git switch main
git pull --ff-only
git switch -c feature/НАЗВАНИЕ_ВЕТКИ
```

Замените `НАЗВАНИЕ_ВЕТКИ` на короткое название своей задачи.

Проверьте, в какой ветке вы находитесь:

```bash
git branch
```

Звёздочка `*` должна стоять напротив вашей ветки.

Перед началом работы обновите `main`, затем подтяните его изменения в свою ветку:

```bash
git switch main
git pull

git switch feature/НАЗВАНИЕ_ВЕТКИ
git merge main
```

Если после обновления изменился `requirements.txt`, дополнительно выполните:

```bash
pip install -r requirements.txt
```

### Как сохранять свою работу

```bash
git status
git add .
git commit -m "Коротко опишите, что сделано"
git push -u origin HEAD
```

При первой отправке `git push -u origin HEAD` создаст ветку на GitHub и настроит
связь с локальной веткой. После этого достаточно `git push`.

Не работайте напрямую в `main`: изменения из рабочих веток добавляем в `main` через Pull Request.

## Структура проекта

- `backend/` — API и независимый процесс расчёта:
  - `api.py` создаёт приложение FastAPI и отдаёт страницу интерфейса;
  - `endpoints.py` содержит HTTP-обработчики последнего прогноза и среднего;
  - `prediction.py` выбирает модель или baseline внутри функции `predict`;
  - `prediction_worker.py` формирует признаки, сохраняет прогнозы и очищает старые результаты;
  - `README.md` описывает задуманную архитектуру и взаимодействие процессов.
- `data/` — работа с входными данными и базами:
  - `ingestion.py` запускает учебный генератор событий и очищает старые события;
  - `storage.py` создаёт таблицы и выполняет запросы SQLite;
  - `local/worker_demo/` содержит две локальные базы: `incoming.sqlite3`
    (события, расписание, счётчик) и `results.sqlite3` (признаки и прогнозы).
    Базы создаются автоматически и не попадают в Git.
- `frontend/index.html` — интерфейс с текущим числом и кнопкой среднего последних 10 значений.
- `scripts/run_demo.py` — совместный запуск и остановка трёх процессов на Linux, macOS и Windows.
- `tests/` — проверки HTTP API, хранения и взаимодействия генератора с worker.
- `.github/workflows/tests.yml` — автоматическая проверка проекта в GitHub Actions.
- `requirements.txt` — внешние Python-зависимости приложения и тестов.
- `.env.example` — пример настроек интервалов, хранения данных и порта.
- `.gitignore` — исключения для локальных баз, окружения, секретов и кэшей.

## Запуск

Нужен Python 3.9+. Команды выполняются из корня репозитория.

Linux и macOS:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python scripts/run_demo.py
```

Windows (PowerShell или cmd):

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe scripts/run_demo.py
```

Откройте http://127.0.0.1:8000. На странице число — текущее состояние
автобуса. Оно обновляется автоматически. Кнопка «Вывести среднее из последних 10»
запрашивает у FastAPI среднее последних 10 сохранённых значений `state`
через `GET /predictions/average` и показывает количество использованных записей. Остановить все три процесса: Ctrl+C
в терминале запуска. Скрипт также останавливает остальные процессы, если один
завершился. Если порт занят, добавьте к команде запуска `--port 8001`.
Скрипт использует текущий интерпретатор Python и сам определяет корень проекта.

## Что происходит

1. `data.ingestion` каждую секунду генерирует числа 0, 1, 2, … и записывает
   валидированное событие с задержкой 0 в `incoming.sqlite3`.
   Таблица `schedule` остаётся пустой.
2. `backend.prediction_worker` раз в 3 секунды читает последнее событие,
   вычисляет признаки и вызывает `predict(features)` для инференса модели.
   Выбор модели и переход на baseline выполняются внутри `predict`, в `backend/prediction.py`.
   Затем worker сохраняет признаки в `features`, а результат — в `predictions`
   вместе с временем расчёта.
   Обе таблицы находятся в `results.sqlite3`.
3. FastAPI только читает результат через `GET /predictions/latest`.
   Страница опрашивает его раз в секунду. Числа могут перескакивать:
   worker берёт последнее состояние, а не каждое событие.

### Время расчёта в логах worker

После каждого цикла worker выводит в терминал строку с датой и временем, например:

```text
2026-09-25 12:00:00,000 prediction worker: cycle status=ok buses=1 features_ms=0.012 predict_ms=0.085 total_ms=2.430 state=42
```

Все длительности измеряются через `time.perf_counter()` в миллисекундах:

- `buses` — количество автобусов, взятых в обработку. В текущем демо это один
  условный автобус (последнее событие), либо 0, если свежих данных нет.
- `features_ms` — время вызова `generate_features`, без сохранения признаков.
- `predict_ms` — время всего вызова `predict`, включая baseline при переключении,
  без операций БД. Источник (`source=catboost`, `source=torch` или `source=baseline`)
  выводится отдельной строкой из функции `predict`.
- `total_ms` — весь цикл, включая чтение БД, признаки, предикт, сохранение
  и очистку старых результатов. Ожидание следующего цикла сюда не входит.
- `status` — `ok`, `no_data` или `error`; `state` — опубликованное значение.

Причина перехода на baseline выводится как предупреждение; при ошибке модели
также выводится traceback. Успешный baseline даёт циклу `status=ok`.
Если ошибка не обработана запасным расчётом, цикл получает `status=error`. У ещё не начавшихся этапов время равно нулю.
Логи выводятся в stderr; отдельный файл автоматически не создаётся.

`predict(features)` в `backend/prediction.py` выбирает функцию по переменной
окружения `MODEL_TYPE`: `catboost` → `predict_catboost`, `torch` → `predict_torch`,
`baseline` (по умолчанию) → `predict_baseline`. Неизвестное значение также
включает baseline с предупреждением. Настройка читается при запуске процесса.
Функции CatBoost и Torch пока выбрасывают `ModelUnavailableError`: сюда нужно
подключить реальные модели. При недоступности или исключении модели `predict`
вызывает `predict_baseline`, который возвращает исходные `state` и `delay`.
Все варианты возвращают словарь с `state` и `delay`, без операций с БД.
Worker вызывает только `predict` и сохраняет результат одной транзакцией с признаками.
Ошибки вычисления признаков, сохранения и самого baseline не запускают повторный
запасной расчёт: старый прогноз сохраняется, ошибка логируется, worker пробует
снова в следующем цикле. Лимит времени выполнения модели пока не установлен.

Это проверка взаимодействия процессов, а не реальная модель задержки.
Расписание пусто, задержка всегда 0, история за 30 минут не требуется.

Базы находятся в `data/local/worker_demo/` и игнорируются Git. Создаются
самими процессами. После перезапуска счётчик продолжается.
Срок хранения событий, признаков и прогнозов
по умолчанию 1800 секунд. Каждый процесс очищает свою базу.

Если worker или генератор остановился, спустя 15 секунд результат считается
устаревшим: страница показывает «—». То же отображается при пустой базе или
недоступном API. Числовой заглушки и принудительного таймаута модели пока нет.
В API сохраняются `predicted_at` и `data_as_of` (UTC).

## Отдельный запуск процессов

В трёх терминалах из корня репозитория (Linux/macOS; на Windows замените
`.venv/bin/python` на `.venv\Scripts\python.exe`):

```bash
.venv/bin/python -m data.ingestion
.venv/bin/python -m backend.prediction_worker
.venv/bin/python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Не запускайте второй генератор или worker одновременно с общим скриптом.
Настройки перечислены в `.env.example`. Автоматической загрузки `.env` нет:
можно задать переменные перед командой или загрузить свой файл в оболочку.
Документация API: http://127.0.0.1:8000/docs.
Архитектура и будущие запросы: [backend/README.md](backend/README.md).

При необходимости скопируйте `.env.example` в `.env` и загрузите настройки
перед запуском (Bash):

```bash
cp .env.example .env
# Отредактируйте значения в .env.
set -a
source .env
set +a
.venv/bin/python scripts/run_demo.py
```

## Зависимости

`fastapi` нужен для HTTP API, `uvicorn` — для сервера, `pytest` — для тестов,
`httpx` — для тестового HTTP-клиента FastAPI. SQLite, работа со временем,
файлами и логированием входят в стандартную библиотеку Python.
Зависимости самого FastAPI (включая Starlette и Pydantic) устанавливает pip.
Отдельная установка JavaScript-пакетов или сервера баз данных не требуется.

## Автоматические проверки при push

Workflow `.github/workflows/tests.yml` запускается на каждый `push` в любую
ветку и на `pull_request`. В Ubuntu с Python 3.9 и 3.12 он устанавливает
`requirements.txt`, проверяет совместимость установленных зависимостей
через `pip check`, синтаксис скрипта запуска через `python -m py_compile scripts/run_demo.py` и выполняет
`python -m pytest -q`.

Сейчас pytest выполняет 22 проверки (с учётом параметризованных случаев):

- Доступность API и HTML-страницы, корректные ответы при отсутствии базы,
  отсутствие создания базы при чтении и отсутствие старого `POST /predict`.
- Среднее для пустой истории, нуля, менее 10 записей и истории длиннее 10;
  используются только последние 10 записей, база не изменяется.
- Ответ среднего до создания таблиц worker.
- Цепочка генератор → worker → API, сохранение результата при повторном чтении
  и переход прогноза в состояние `stale`.
- Удаление устаревших данных и сохранение счётчика после повторной инициализации.
- Откат записи признаков и прогноза при ошибке сохранения.
- Замеры этапов, успешный вызов модели, baseline при отсутствии или ошибке модели
  и сохранение предыдущего прогноза при ошибке baseline.

Это проверки API и данных; автоматических браузерных тестов интерфейса пока нет.
Локально тот же набор запускается так:

```bash
.venv/bin/python -m pip check
.venv/bin/python -m py_compile scripts/run_demo.py
.venv/bin/python -m pytest -q
```
