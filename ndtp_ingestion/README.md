# NDTP → общая база

Исходный модуль помощника перенесён из `main`, коммит `99b115b`. Он принимал TCP на 9000, распознавал handshake и навигацию, писал SQLite, загружал CSV расписания и каждые 10 минут удалял телеметрию с `receive_time` старше двух часов. План и прогнозы не очищались.

При интеграции исправлены: явная карта `unit_id → tr_id` вместо подмены ID; чтение `geom` из исходного CSV; единый `DATABASE_URL`; схема и уникальность прогнозов из ML; повторный импорт плана без дублей; CRC, границы пакетов, флаги координат, время и скорость. Неизвестные устройства и плохие пакеты отбрасываются с записью причины в журнал. Поддерживается навигация первой ячейкой, как в поставляемом эмуляторе; остальные датчики для ML не нужны. Проверки и координатная область ориентированы на московскую модель, а не на произвольные NDTP-устройства.

## Общий запуск

Из корня проекта, существующая `.venv` Python 3.12:

```bash
bash scripts/setup_and_run.sh --mode emulator --demo-plan
```

Скрипт стартует приёмник, ML, API и локальный Docker-эмулятор. Интернет не нужен, если зависимости и образ/архив уже доступны. Docker должен быть запущен и доступен пользователю. Автозапуск контейнера использует host network и поддержан на Linux. API — http://127.0.0.1:8000, NDTP — 9000, REST эмулятора — 18080. Ctrl+C останавливает все процессы и только созданный этим запуском контейнер.

**`--demo-plan` создаёт искусственное расписание на ближайшие два часа и три демонстрационных ТС. Автогенератор движется случайно, не по реальному маршруту. Это проверка соединения модулей, а не качества модели.** База каждого такого запуска новая (`artifacts/emulator-demo-*.db`); старые файлы не удаляются. Необязательный `--db` позволяет явно выбрать базу. CSV телеметрии в этом режиме не импортируется.

## Свой актуальный план

```bash
bash scripts/setup_and_run.sh --mode emulator \
  --schedule /path/to/current-plan.csv \
  --unit-map /path/to/units.json \
  --emulator-config /path/to/emulator.json
```

Пример `units.json`: `{"1166336": 122658}`. Это **пример**, соответствие должно быть подтверждено вашим источником данных. CSV: `tt_action_item_id,tr_id,time_begin,manual_fill,geom,building_address` (последнее поле необязательно). Вместо `geom` можно передать `lon,lat`. Время UTC. `time_fact_begin` не импортируется. План должен покрывать текущее время и горизонт +10…15 минут. Январский `schedule.csv` здесь не актуален.

В конфиге эмулятора при автоматическом Linux-запуске используйте `targetHost: "127.0.0.1"`, `targetPort: 9000`, единицы из карты. Формат конфигурации — в `data/dataset/docs/Emulator-and-Telematic-Packets-Specification.md`.

Для эмулятора, запущенного отдельно, передайте `--no-emulator` вместо `--emulator-config`; настройте его адрес назначения вручную. Это также вариант для macOS/Windows. Скрипт не подменяет конфигурацию уже работающего контейнера на 18080.

Низкоуровневые команды (общие `DATABASE_URL` и `NDTP_UNIT_MAP`):

```bash
python -m ndtp_ingestion.db_init
python -m ndtp_ingestion.load_schedule /path/to/current-plan.csv
python -m ndtp_ingestion.server
```

С SQLite используется WAL, ожидание блокировки записи — 30 с. Дубли точек определяются по `(tr_id,event_time)`: максимум одна точка в секунду на ТС, как позволяет время эмулятора. Запоздавшие точки до двух часов принимаются, исходное время сохраняется; будущее свыше 60 с отклоняется. CRC проверяется согласно спецификации поставляемого эмулятора.

## Очистка

Работает только при запущенном приёмнике, на старте и каждые `CLEANUP_INTERVAL_S` (600 с). Удаляет строки, а не уменьшает размер SQLite-файла автоматически.

| Таблица | Правило по умолчанию | Настройка |
|---|---|---|
| telemetry | `receive_time` старше 2 часов | `TELEMETRY_RETENTION_S=7200` |
| schedule_plan | `time_begin` старше 6 часов; будущий план сохраняется | `SCHEDULE_RETENTION_S=21600` |
| predictions | `predicted_at` старше суток | `PREDICTIONS_RETENTION_S=86400` |

Телеметрия должна храниться дольше окна ML с запасом минимум 60 с; план — минимум 6 ч для признаков. Число удалённых строк журналируется. Историческое демо приёмник не запускает и историческую базу не очищает. Существующая база от старой версии может потребовать новой схемы: используйте отдельный файл `--db`, автоматического удаления старых данных нет.

## Отдельный контейнер приёмника

Собирается **из корня**: `docker build -f ndtp_ingestion/Dockerfile -t ndtp-server .`. Передайте `DATABASE_URL`, `NDTP_UNIT_MAP`, смонтируйте общую базу и карту устройств, пробросьте 9000. План загрузите заранее. Для локальной проверки проще общий скрипт выше.
