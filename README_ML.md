# ML-модуль: прогноз задержки на 10-15 минут вперёд

## Результаты

Метрика хакатона - MAE (сек) задержки на целевой остановке. Скор платформы
считается как `(mae_zero − MAE) / (mae_zero − MAE_TARGET)`. Baseline
`prediction = cur_dev_s` даёт скор ≈ 0.40, отсюда `MAE_TARGET ≈ 78 с` (оценка по test).

| Модель | CV по ТС, MAE (реальные ТС) | Holdout train→test, MAE | Оценка скора |
|---|---|---|---|
| baseline «задержки нет» | 93.0 | 103.3 | 0.00 |
| baseline `cur_dev_s` (подсказка) | 88.4 | 93.4 | 0.40 |
| Huber-регрессия (линейная) | 75.4 | 77.2 | 1.00 |
| RandomForest | 54.7 | 55.3 | 1.00 |
| ExtraTrees | 53.6 | 52.8 | 1.00 |
| XGBoost | 47.7 | 48.6 | 1.00 |
| LightGBM | 47.6 | 46.4 | 1.00 |
| sklearn HistGB | 47.7 | 45.5 | 1.00 |
| CatBoost (Huber, depth 8) | 45.8 | 44.3 | 1.00 |
| Ансамбль бустингов CatBoost + LightGBM + XGBoost | 46.2 | 45.8 | 1.00 |
| PyTorch: GRU только по телеметрии (+ предобучение) | 52.4 | 51.8 | 1.00 |
| PyTorch: GRU + табличные признаки, без предобучения | 50.4 | 47.6 | 1.00 |
| PyTorch: GRU + табличные признаки + предобучение | 45.0 | 42.7 | 1.00 |
| **Финальная модель: 0.4 × бустинги + 0.6 × GRU** | **41.9** | **40.6** | 1.00 |

Режим **stream**: подсказки `cur_dev_s` нет, работаем только по телеметрии и плану.
Так будет в живом потоке от эмулятора.

| stream | CV | Holdout |
|---|---|---|
| Ансамбль бустингов | 51.2 | 52.3 |
| GRU + таблица + предобучение | 49.5 | 45.8 |
| **Бленд 0.45 × бустинги + 0.55 × GRU** | **46.3** | **44.3** |

Итог: MAE снижена в **2.3 раза** относительно baseline (93 → 41 с). Скор
упирается в потолок 1.0 с большим запасом: для 6 баллов нужен скор ≥ 0.70.

Что дала нейросеть:

- **Самообучение даёт больше всего.** Предобучение энкодера на ТС без
  разметки улучшает MAE сети с 50.4 до 45.0 с.
- **Бленд с бустингами** даёт ещё −4 с к лучшей одиночной модели. Сеть и
  бустинги ошибаются по-разному.
- **Сеть без табличных признаков** (только сырая последовательность GPS и
  `cur_dev_s`) уже лучше RandomForest на 49 вручную собранных признаках.

Веса бленда (0.6 / 0.55) подобраны по OOF-прогнозам CV на тех же фолдах, что
и у бустингов (`artifacts/model/blend_{mode}.json`).

### Раннее предупреждение (holdout: обучение только на train, `python -m ml.backtest`)

| | hint | stream |
|---|---|---|
| MAE финальной модели (бустинги + GRU) | **40.6** | **44.3** |
| ROC-AUC «опоздание > 120 с» по прогнозу задержки | **0.968** (baseline 0.777) | **0.974** |
| Правило «прогноз > 120 с»: precision / recall | 0.83 / 0.78 | 0.87 / 0.79 |
| То же для baseline `cur_dev_s > 120` | 0.47 / 0.51 | 0.47 / 0.51 |
| Покрытие интервала 10–90% | 0.77 | 0.79 |
| Горизонт (мин): min / медиана / max | 11 / 11 / 15 | 11 / 11 / 15 |
| Прогнозов до наступления события | 100% | 100% |

Горизонт соблюдается по построению. Целевая остановка - первая с плановым
временем в `(T+10, T+15]` мин. Признаки строятся только по телеметрии с
`t ≤ T` и плану, поэтому «прогнозов задним числом» не бывает.

## Как устроено

```
телеметрия ТС (t ≤ T) ─┐                                   ┌─► ансамбль бустингов ─────────┐ 0.4
плановое расписание ТС ─┼─► compute_features ─► 49 признаков ┤                               ├─► задержка, с
cur_dev_s (если есть) ─┘                                   └─► ┐                           │
                       └─► build_sequence ─► 120×7 (30 мин) ───┴─► PyTorch GRU + MLP ──────┘ 0.6
                                                      49 признаков ─► CatBoost-квантили ─► интервал 10–90%
```

Модели предсказывают **остаток** `target − cur_dev_s`: насколько задержка
изменится за ближайшие 10–15 минут.

### Нейросеть (`ml/sequence.py`, `ml/nn_model.py`, `ml/train_nn.py`)

**Вход.** Последние 30 минут телеметрии на сетке 15 с (120 шагов × 7 каналов):

- есть ли свежая точка (разрывы связи);
- скорость и перемещение за шаг;
- расстояние до плановой позиции со сдвигом на текущее отклонение (насколько
  ТС уходит от нитки графика);
- расстояние до ближайшей плановой остановки (стоянка на остановке или в заторе);
- есть ли у ТС план;
- позиция шага в окне.

**Архитектура.** `Conv1d(k=4, stride 2) → GRU(64)` по последовательности,
`MLP` по 49 табличным признакам (стандартизация, NaN → 0 плюс маска пропуска),
общая голова. На выходе - остаток задержки. Лосс Huber (δ = 150 с),
AdamW + OneCycle, 60 эпох, усреднение по 3 сидам.

**Предобучение (self-supervised).** 16.7 тыс. окон с 43 ТС, которых нет в
test/validate: 26 синтетических и 17 реальных ТС без разметки, у 17 из них
нет даже плана. Энкодер учится по прошлым 30 минутам предсказывать будущее
движение: скорость за 5 и 10 мин, путь, долю стоянок и отход от плановой
позиции через 10 мин. Разметка задержек в предобучении не используется.
После этого вся сеть дообучается на размеченных точках.

### Признаки (`ml/feature_engineering.py`)

1. **Выравнивание трека по графику.** Плановое положение ТС в момент `t`
   получаем интерполяцией координат остановок по плановым временам. Ищем сдвиг
   δ ∈ [−10, +15] мин, при котором трек за последние 3/10/20 мин лучше всего
   совпадает с планом в `t − δ`. Это свежая оценка текущего отклонения по GPS
   (**map matching к нитке графика**).
2. **Детекция проходов остановок** (минимум расстояния до остановки < 60 м):
   отклонения на последних остановках, их тренд и экстраполяция.
3. **Движение:** средняя скорость за 5/10 мин, скорость в движении, доля
   стоянок, текущий простой (dwell), пройденный путь, разрыв связи, доля валидных GPS.
4. **План впереди:** число остановок и расстояние до цели, плановая скорость,
   запас времени в графике.
5. **Структура рейса:** отстой или разворот впереди (разрыв в плане ≥ 4 мин),
   сколько прошло и осталось до конца рейса. Самый сильный эффект: после отстоя
   задержка «сбрасывается», первая остановка рейса почти всегда вовремя.
6. **Время суток.**

Очистка: невалидные координаты, координаты вне Москвы и скорость > 120 км/ч
выбрасываются. Время точки = `max(event_time, receive_time)`, то есть точка
считается известной, только когда она уже получена.

### Анти-утечка

- Фактические времена прибытия (`time_fact_begin`) **не используются нигде**.
  Из `schedule.csv` берутся только плановые колонки. Признаки train, test и
  validate считаются одним и тем же кодом.
- В раздаче есть утечка: `test/schedule.csv` и `train/schedule.csv` содержат
  факт по всем целевым остановкам validate, а телеметрия test и validate
  одинаковая. Мы её **сознательно не используем** (правило честности README).
  Если жюри спросит - это аргумент в нашу пользу.
- Валидация: GroupKFold по `tr_id` и отдельный holdout train→test. Метрика
  только по реальным ТС: синтетика есть лишь в train, она помогает как объём
  данных (понижение её веса ухудшало CV).

## Команды

```bash
pip install -r requirements-ml.txt

# 1. признаки (~30 с); validate/traffic.csv = test/traffic.csv
python -m ml.dataset --data data/dataset --out artifacts/features
# 2. сравнение моделей (~5 мин на режим)
python -m ml.train compare --mode hint
python -m ml.train compare --mode stream
# 3. финальные модели на train+test (~3 мин)
python -m ml.train fit
# 3b. нейросеть: последовательности (~30 с), сравнение и вес бленда (~40 мин на CPU), финальные веса (~10 мин)
python -m ml.train_nn build --data data/dataset
python -m ml.train_nn compare --mode hint
python -m ml.train_nn compare --mode stream --only-best
python -m ml.train_nn fit
# 4. бэктест раннего предупреждения
python -m ml.backtest
# 5. сабмит
python -m ml.make_submission --data data/dataset --out artifacts/submission.csv
# 6. сервис и воркер
uvicorn ml.service:app --port 8001      # Swagger: http://localhost:8001/docs
python -m ml.csv_to_db --data data/dataset --url sqlite:///artifacts/demo.db   # тестовая база из CSV
DATABASE_URL=sqlite:///artifacts/demo.db python -m ml.worker --once
python -m pytest -q
```

## Интеграция с остальными модулями

### Поток данных

```
NDTP / реплей ─► обработчик входа ─► ОБЩАЯ БАЗА: telemetry, schedule_plan
                               │
                               ▼  раз в 30 с
                      ML-воркер (python -m ml.worker)
                               │  прогноз задержки по всем ТС
                               ▼
                         таблица predictions той же базы
                                 │
                                 ▼
                      FastAPI бэкенда ─► интерфейс
```

ML-модуль сам читает базу, которую заполняет `ndtp_ingestion.server`, и сам
пишет результат в таблицу `predictions`. Для отдельного исторического режима входные таблицы
наполняются `ml.csv_to_db`. Живой запуск и сроки очистки описаны в `ndtp_ingestion/README.md`. Обработчик входа отвечает и за удаление устаревших
строк из общей базы. HTTP API (`/predict`, `/predict/batch`) остаётся для
Swagger и ручной проверки; интерфейс читает FastAPI бэкенда.

### Что ML читает из базы

Имена таблиц и колонок задаются переменными окружения (полный список - в
docstring `ml/db.py`). По умолчанию они совпадают с колонками CSV, так что если
Backend кладёт данные «как в CSV», настраивать ничего не нужно.

| Таблица | Колонки (по умолчанию) | Примечание |
|---|---|---|
| `telemetry` | `tr_id`, `event_time`, `receive_time`, `lon`, `lat`, `speed`, `location_valid` | индекс `(tr_id, event_time)`; ML берёт последние 45 мин |
| `schedule_plan` | `tt_action_item_id`, `tr_id`, `time_begin`, `geom` (`POINT (lon lat)`) или `lon`/`lat`, `manual_fill` | **только план** - без `time_fact_begin` |
| текущая задержка (необязательно) | `tr_id`, `cur_dev_s` | включается `ML_CURDEV_TABLE`; без неё ML оценивает задержку по GPS |

- Подключение: `DATABASE_URL`, например `postgresql+psycopg2://user:pass@db:5432/transport`.
- Все времена трактуются как UTC (как в датасете).
- Момент прогноза `T`: по умолчанию (`ML_TIME_MODE=stream`) - время последней
  точки телеметрии в базе. Это нужно для реплея исторических данных. Для живого
  потока - `ML_TIME_MODE=wall` (текущее время).

### Что ML пишет в базу: таблица `predictions`

Создаётся автоматически. Каждый цикл дописывает строки (история сохраняется,
актуальный прогноз - строка с наибольшим `t_forecast` по `tr_id`).
Повторный цикл для одной комбинации ТС, времени и остановки не создаёт дубль.

| Колонка | Смысл |
|---|---|
| `tr_id` | ID ТС |
| `t_forecast` | момент потока `T`, на который сделан прогноз |
| `predicted_at` | когда сделан прогноз (время сервера, UTC) |
| `target_stop_id`, `target_time_plan` | целевая остановка (первая в окне T+10…15 мин) и её плановое время |
| `predicted_delay_s` | **прогноз задержки, сек** (+ опоздание, − опережение) |
| `predicted_arrival` | прогноз прибытия = план + задержка |
| `interval_lo_s`, `interval_hi_s` | интервал прогноза задержки 10–90% |
| `model_used` | `ensemble` / `boosting` / `catboost` / `torch` / `baseline` |
| `fallback_reason` | почему ответил бейзлайн (пусто, если модель) |
| `degraded` | нет свежей телеметрии > 2 мин - прогноз по последнему состоянию |

Актуальные прогнозы (PostgreSQL):

```sql
SELECT DISTINCT ON (tr_id) * FROM predictions ORDER BY tr_id, t_forecast DESC, id DESC;
```

### HTTP API (Swagger, ручная проверка)

- `POST /predict/from-db` - один цикл по базе прямо из Swagger (то же, что делает воркер).
- `POST /predict`, `POST /predict/batch` - прогноз по состоянию ТС, переданному в запросе:

```json
{
  "tr_id": 134040,
  "T": 1767675000,                 // момент прогноза: unix-сек или ISO "2026-01-06T04:50:00"
  "cur_dev_s": 357.0,              // необязательно: без него режим stream
  "plan": [{"stop_id": 53698328398, "time_begin": 1767675720, "lon": 37.71, "lat": 55.62, "manual_fill": false}, ...],
  "telemetry": [{"t": 1767674990, "lon": 37.70, "lat": 55.62, "speed": 18, "valid": true}, ...]
}
```

Ответ:

```json
{
  "tr_id": 134040, "T": 1767675000, "predicted_at": 1790342402.6,
  "target_stop_id": 53698328398, "target_time_plan": 1767675720,
  "predicted_delay_s": 273.4, "predicted_arrival": 1767675993.4, "interval_s": [214.3, 399.8],
  "model_used": "ensemble", "fallback_reason": null,
  "mode": "hint", "degraded": false, "inference_ms": 3.8
}
```

### Переключатель модели и откат на бейзлайн

Модель выбирается переменной окружения `MODEL_TYPE` (в docker-compose - `environment`):

| `MODEL_TYPE` | Что считает |
|---|---|
| `ensemble` (по умолчанию) | 0.4 × бустинги + 0.6 × нейросеть; если torch не загружен - честно `boosting` |
| `boosting` | среднее CatBoost + LightGBM + XGBoost |
| `catboost` | только CatBoost |
| `torch` | только нейросеть PyTorch |
| `baseline` | прогноз = текущая задержка (`cur_dev_s`) |

Сервис никогда не падает из-за модели:

- Модель не загрузилась при старте - все ответы бейзлайном, `/health` вернёт
  `status: degraded` и текст ошибки.
- Сломались признаки конкретного ТС - бейзлайн только для этого ТС.
- Упала модель на батче - бейзлайн для батча.

В каждом ответе `model_used` - какая модель реально посчитала прогноз, а
`fallback_reason` - почему ответил бейзлайн (`null`, если не он). Дашборд может
помечать такие прогнозы серым.

ТС, у которых в окне 10–15 мин нет плановой остановки (конец смены, долгий
отстой), попадают в `skipped` с причиной. Это не ошибка.

## Что можно улучшить дальше

- Transformer вместо GRU и более длинное предобучение: пул можно расширить
  окнами с шагом 30 с вместо 90 с.
- Инференс сети через ONNX Runtime вместо torch: файлы уже экспортируются.
- What-if: ML-сервис принимает произвольный план, поэтому можно подать
  изменённый план (сдвиг выпуска, резервное ТС) и сравнить прогнозы.
- Классификатор «опоздает > 2 мин» поверх регрессии, когда до него дойдёт очередь.
